# Experimental opt-in connection pool

This proposal adds `client.NewReconnectableClientPool(configFunc, connectedFunc, lazy, size)` to the Go core API. Existing constructors and the standard CLI configuration are unchanged. The CLI configuration/API shape and the congestion-control policy still need maintainer agreement in [#1431](https://github.com/HyNetworks/hysteria/issues/1431).

- Size 1 delegates to the existing reconnectable client. Sizes 2 through 8 create independent reconnectable QUIC connections; the upper bound is a resource guard, not a recommendation.
- New TCP streams and Hysteria UDP sessions are assigned round-robin. Existing streams/sessions remain on their selected connection. A failed open is returned to the caller; there is no transparent replay, migration, packet striping or single-stream speedup.
- Lazy mode opens each connection on its first selected flow. Eager initialization fails as a whole and closes already initialized members if a later member cannot initialize.
- Config evaluation and success callbacks are serialized within the pool. The success callback receives the connected member and a pool-wide count of successful handshakes, including initial connections and reconnects. A custom connection factory must provide independent packet connections and support concurrent members.
- Nonzero client bandwidth targets are split statically and evenly. Remainders are assigned in bytes/s so the member targets sum to the configured target. Zero targets remain zero. Idle members' allocations are not redistributed. This does not implement a shared limiter or guarantee the aggregate wire rate; loss compensation and server-side per-connection limits still apply.
- `Close` closes all members, aggregates errors, waits for concurrent closes and is idempotent. Established flow ownership remains with each underlying reconnectable client.

## Scope and unresolved questions

No GRO, receive recycling, diagnostic packet logging, quic-go dependency changes, OpenWrt configuration or CPU-overclock code is included. The public pool API is provisional, and the bound of eight members is a conservative implementation choice for review. Eight is covered by unit tests and TCP/UDP integration tests, not router performance validation. Integration tests include eager/lazy startup, Chrome parroting enabled/disabled, UDP fragmentation and member recovery after local socket failure while healthy members' established TCP flows remain usable.

The inherited reconnectable client's terminal-error transport cleanup issue remains under review in [#1696](https://github.com/HyNetworks/hysteria/pull/1696). A real server-stop/idle-timeout probe confirmed an open retired UDP socket on the unmodified base, and passed five race-enabled repetitions, each with three server restarts and successful TCP recovery, when the proposed #1696 cleanup was applied locally. This PR does not bundle that separate fix. Merge/production readiness requires resolving that lifecycle issue; local-socket-failure tests alone are not proof of cleanup after a peer failure or of long-term absence of leaks.

The paired historical prototype results in [#1431](https://github.com/HyNetworks/hysteria/issues/1431#issuecomment-6146553555) showed approximately 35% higher aggregate download throughput but included custom receive-path changes on both sides. A separate [pool-only experiment](CONNECTION_POOL_BENCHMARK.md) on current upstream dependencies, preserving the router's existing runtime OC, measured approximately 28% higher download median. It also observed UDP memory errors, ICMP misses and isolated DNS timeout warnings. Neither experiment establishes loss-free long-term stability or justifies a new default.
